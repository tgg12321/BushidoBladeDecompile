### Coverage legend

- **COVERED** - A documented pure-C recipe has retired this family before.
- **PARTIAL** - Recipes exist for SOME shapes in this family; the family is heterogeneous, so per-rule triage is needed.
- **COVERED-FORBIDDEN** - Named FORBIDDEN cheat family with a documented pure-C replacement recipe. These rules must go; the recipe is known.
- **OPEN** - No documented recipe retires this family. Open problem.
- **OPEN-CANONICAL** - No pure-C recipe; the disposition is the canonical-asm grant path (STRONG scanner evidence + Judge), not a C lever.

## 2. Recipe-coverage assessment per family group

### 2a. Register-allocation divergence - 867 rules (53% of the file)

`register-rename` (666) + `register-swap-range` (80) + `frame-reg-rename` (27) + `register+displacement` (70) + `operand-order-swap` (24).

This is the single dominant fact about regfix.txt: **more than half of all rules are one register substituted for another**.
Recipe coverage is genuinely good here - `.claude/rules/` carries SEVEN distinct pure-C levers that have retired
RA-divergence clusters before:

- `register-alloc-pure-c` - the Step-0 anomaly diagnosis (`-da` greg dump) + Levers A/B/C; the umbrella recipe.
- `compare-operand-order-register` - `$X <-> $Y` rename over paired comparisons -> reverse the comparison operand order. **Directly targets `operand-order-swap` and a subset of `register-rename`.**
- `call-return-if-result-reuse-v0` - mirror-image rename cluster -> init the if/else result var from the call return.
- `restore-discarded-return-displaces-v0` - `$v0`->`$v1` substitution on a post-call lw/sw pair.
- `drop-param-alias-local` - param->local alias -> drop the alias.
- `exit-path-return-set-cse-join` - shared finish label copy into `$v0`.
- `hoist-shared-arm-computation-defeats-copy-pref` - duplicated `z = x + y` across arms.
- `duplicated-statement-into-arms` - the proven byte-free ref-lift for global-RA priority walls.

**Assessment: COVERED, but the recipes are diagnostic rather than mechanical.** Each is keyed to a
specific *cluster shape* (mirror-image pair, post-call lw/sw pair, paired comparisons), so the campaign
work is pattern-matching each function's rename cluster to the right recipe - not applying one transform en masse.
`register-asm-pins` is explicitly DIAGNOSTIC-ONLY and never committable, so there is no shortcut.

### 2b. Scheduling / delay-slot divergence - 100 rules

`reorder-scheduling` (91) + `nop-scheduling-insert` (8) + `fill-delay-slot` (1).

Best-covered family in the whole file. The index lists 10 scheduling recipes:
`loop-exit-work-inside-loop-sched-fence`, `loop-note-fixes-delay-slot-steal`, `loop-counter-fills-load-delay`,
`walking-pointer-serializes-parallel-loads`, `hoist-call-arg-local-flips-jal-delay`, `store-before-jal`,
`defer-store-past-later-compute-into-jal-delay`, `switch-break-shared-return-sched-hoist`,
`fake-varargs-explicit-homing`, `split-scalars-hide-aggregate`. Plus `maspsx-label-nop-gate` for the
single-nop-before-a-load-in-a-loop case (a per-function maspsx gate, explicitly "do not park").

**Assessment: COVERED, highest confidence in the file.** These recipes have measured multi-session provenance.

### 2c. Frame / stack-slot divergence - 196 rules

`frame-stack-offset` (73) + `memory-displacement` (123).

`phantom-slot-frame-lever` (2026-08-04) is the diagnosis recipe: target frame reserves untouched bytes,
with three measured honest producers plus a `.frame vars=` gradient instrument. It closed `func_8003D9A0`
and `func_8003DBE4`. The 2026-08-17/18 owner rulings additionally sanction an unwritten `volatile u32 pad[N]`
leading (and, for `func_8003CF84` only, trailing) local - but that scope is **explicitly three functions**
and does not generalize.

The `memory-displacement` half is heterogeneous: some rules are pure stack-slot rotation (`CD_datasync`'s
`,24(` -> `,32(` chain reads as an allocation-order rotation), others are struct-offset shifts that point at
`defeat-combine-symbol-fold` or a header-level type/layout correction.

**Assessment: frame-stack-offset COVERED (diagnosis recipe + frame census locator); memory-displacement PARTIAL** - needs per-cluster triage to split rotation from layout.

### 2d. Lost-codegen / instruction injection - 123 rules (FORBIDDEN families)

`instruction-injection-insert` (70) + `lost-codegen-nop-fill` (27) + `lost-codegen-move-insert` (26).

These are the rules `lost-codegen-insert-cheat.md` names outright. That rule documents 29 grandfathered
functions / 39 instructions as of 2026-05-16; **the current count is 123 rules across 38 functions**, so the population is substantially larger than the grandfather list once the generalized shapes are counted:

- `lost-codegen-move-insert` (26) is the literal named shape (`insert_after "addu $rN,$rM,$zero"`).
- `lost-codegen-nop-fill` (27) is the SAME cheat spelled as `subst "nop" "<real insn>"` - it writes an instruction
  GCC never emitted over a nop slot. The rule file does not name this spelling.
- `instruction-injection-insert` (70) is the generalized form: a single `la` / `addiu` / `lui` / `ori` the compiler
  did not produce. Same kind as the named cheat, larger payload vocabulary.

**Assessment: COVERED-FORBIDDEN.** The recipe is `shared-end-label` (restructure per-case `return s2;` to
`goto end; ... end: return s2;`) for the const-prop-ate-it case, which `lost-codegen-insert-cheat.md` says to try FIRST.
That rule also lists five techniques that have measurably NOT worked, which saves re-derivation.
For the `la`/`lui`/`ori` payloads the recipe surface is different - `defeat-combine-symbol-fold` and
`store-const-reload-cse` are the likely levers, but neither has been exercised against this exact shape.

### 2e. Control-flow shape - 69 rules

`branch-label-retarget` (54) + `label-insert` (10) + `label-rename` (4) + `branch-insert` (1).

Recipes: `switch-vs-ifchain-branch-sense` (branch-sense-swap rules on ONE case of a dispatch -> write a real
`switch`), `cross-jump-call-merge` / `cross-jump-store-tail-merge` (target has MORE call sites / `j END` tails),
`shared-end-label` (the inverse), `explicit-rejection-set-defeats-range-fold`.

`label-rename` (4 rules) is a different thing entirely - it renames cc1-generated `{lbl#N}` slots to stable
names so sibling rules survive cc1's file-global label counter moving. That is rule *infrastructure*, not a
codegen cheat, and it retires automatically when the rules it serves retire. See `global-label-drift-sibling-cheat`.

**Assessment: PARTIAL.** `switch-vs-ifchain-branch-sense` is narrow (one case of a dispatch). Multi-branch
retarget clusters are not covered by any single recipe.

### 2f. Width / opcode respelling - 206 rules

`delete-instruction` (121) + `opcode-change` (60) + `instruction-suppress-to-nop` (13) + `width-sign-opcode-change` (12).

Width/sign has excellent coverage: `halfword-index-srl-sra`, `u16-global-lhu-lbu-low-byte`,
`narrow-stack-param-subword-offset`, `narrow-byte-args-packed-call`, `bitfield-direction-divergence`,
`header-type-correction-from-use-sites` (four-prong gate). **COVERED.**

`delete-instruction` and `instruction-suppress-to-nop` are the inverse of lost-codegen: OUR build emits
something target does not. Levers: `store-const-reload-cse` (store-then-reload folded to `li`),
`defeat-licm-hoist-var-reuse`, `hoist-flag-load-defeat-add-combine`, `split-read-defeats-hoist`,
`defeat-combine-symbol-fold`. **PARTIAL** - the recipes exist but selecting one requires knowing WHICH
optimizer pass produced the extra instruction, and a `delete` rule text alone does not say.

`opcode-change` (60) is the weakest-covered subgroup. Inspection shows most of these are not single-opcode
corrections at all but *whole-region instruction-stream rewrites* expressed one line at a time - e.g.
`func_8003800C` rewrites five consecutive slots (`addu`->`lui`, `addu`->`lui`, `lui`->`ori`, `lui`->`addu`,
`ori`->`addu`), which is a scheduling/spelling rotation of a region, not five independent opcode fixes.
**Treat contiguous `opcode-change` runs as ONE finding, not N.**

### 2g. No-C-form / canonical territory - 52 rules

`gte-cop2-respell` (16) and `scratchpad-abs-address` (11) are covered by `gte-3x3` / `scratchpad-gte` /
`inline-asm-allowed` - cop2 ops have no C analog and inline `__asm__` for them is canonical.

`whole-body-asm-replace` (11) and `splice-large-asm` (8) are the genuinely OPEN territory. These are not
pure-C problems with an undiscovered lever - they are functions whose entire body (or a large region) is
reproduced from literal rule text. Under `judge-sole-gate` (owner ruling 2026-08-18) their disposition is the
**pipeline canonical-asm grant path**: `tools/scan_hand_coded.py` STRONG (S1/S2/S6) evidence + Judge verdict +
driver-written `inline_asm_canonical.txt` entry + borderline-ledger row. Without STRONG evidence they stay
INCOMPLETE and pure-C search continues. They should NOT be ground as pure-C-lever work until the scanner has run.

## 5. Proposed campaign ordering

The queue is already pre-ordered easiest-first by honest distance and project policy is **no cherry-picking,
no deferral** - the Grinder works the top active item. This map is therefore NOT a proposal to re-order the
queue. It is a *modality* map: for whichever function is on top, it tells you which recipe to reach for first,
and it identifies where a single derivation would pay off across several carriers.

Ordering rationale, in tiers:

**Tier 1 - single-family, small-N, recipe-covered, low distance.** One rule shape, one recipe, few rules.
These are where a recipe application either works immediately or fails informatively.

**Tier 2 - batch clusters.** Functions in the same file sharing a dominant family (section 4). Deriving the
lever once and testing it against every cluster member is strictly better value than one function at a time.

**Tier 3 - lost-codegen carriers.** FORBIDDEN family, known first-move recipe (`shared-end-label`), and
`lost-codegen-insert-cheat.md` documents five approaches that measurably do NOT work - so failure is cheap.

**Tier 4 - mixed-family high-rule-count carriers.** Many rules, several families. Expect multi-session work.

**Tier 5 - whole-body / large-splice carriers.** Run `tools/scan_hand_coded.py --single <func>` FIRST. These
are canonical-asm-grant candidates, not pure-C grinding targets, and grinding them in C before the scanner runs
wastes sessions.

## 6. Caveats on this classification

- Families are derived from **rule text only**. A `subst` that renames a register is classified
  `register-rename` regardless of whether the underlying cause is allocation, scheduling, or a layout shift
  that happened to move a register. The taxonomy narrows the search; it does not diagnose.
- Contiguous runs of `opcode-change` / `register-rename` at adjacent indices are usually ONE region rewrite
  counted N times. Rule COUNT overstates finding count, probably by a large factor on the high-N carriers.
- Recipe slugs are the *first* thing to try, chosen by family shape. The technique index is explicit that
  these rules encode measured multi-session findings - read the rule file before grinding, do not re-derive.
- `engine/queue.json` distance is the honest cheat-free pure-C distance with regfix/asmfix disabled and
  cheat-asm stripped, so it is directly comparable across carriers.

## 7. Surprises worth acting on

**1. The current queue top is a whole-body asm carrier, not a pure-C grind.** `func_80017848` (`ings`,
distance 16) is the top ACTIVE queue item, and both of its rules are in `asmfix.txt`:
`delete_between "^\.frame" "^\.end\s+func_80017848$"` followed by an `insert_before` that supplies the
entire function body (prologue through `jr $ra`) as literal asm. Nothing about the queue entry itself
signals that. Under `judge-sole-gate` the disposition is `tools/scan_hand_coded.py --single func_80017848`
first; if the evidence is not STRONG, it is a pure-C problem whose true starting distance is the whole body,
not 16.

**2. Eleven more carriers have the same hidden shape.** `func_8008C1E8`, `func_8001B748`, `func_800283D0`
use `replace_with_asmfile` (the entire `asm/funcs/<func>.s` substituted in); `func_8002E6B0`,
`func_8003EB84`, `func_8002CA8C` use the same `.frame`/`.end` delete-and-reinsert as the queue top.
Three of them (`func_800283D0`, `func_8002E6B0`, `func_8002CA8C`) are all in `code6cac_b` - if there is a
shared reason (a fork-divergence crash, a hand-written region, an unsplit TU), one scanner pass answers
for all three.

**3. The lost-codegen population is 3x the grandfather list, because two spellings were never counted.**
`lost-codegen-insert-cheat.md` records 29 functions / 39 instructions as of 2026-05-16 and says `--check-new`
only flags NEW additions. The literal `insert_after "addu $rN,$rM,$zero"` shape is 26 rules today - but

single-instruction `insert "la $4,SYM"` / `insert "addiu $2,$zero,1"` style injections number 70. All three
are the same act (bytes from rule text, not from compilation) in different rule verbs. The audit's
lost-codegen detector is keyed to the `addu`-move payload, so 97 of the 123 rules in this family are outside
what `audit_asm_cheats.py --check-new` would flag.

**4. Recipe coverage is high but shallow.** 68.9% of rules land in a family with a documented recipe, but
52.8% of ALL rules (867) are one register substituted for another - a single family whose "recipe" is really eight
different cluster-shape-keyed levers plus a diagnostic dump procedure. The coverage number should not be read
as "two thirds of the file has a known fix"; it means "two thirds of the file has a known place to start."

**5. The lowest-distance carriers are all parked.** The 15 lowest-distance rule carriers - down to
`func_80038C70` at distance 1 with a single rule - are `parked` without exception. The lowest-distance ACTIVE
carrier is the whole-body-asm one from finding 1. Whatever the parks are for, the effect is that the
cheapest-looking regfix retirements are not reachable through the queue.
