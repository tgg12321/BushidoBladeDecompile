# Tree-wide per-file `-G8` adoption census — 2026-08-05

Closing deliverable of Campaign 5, after the `text1a` adoption landed (`6e11d4da`, `cddd4bd1`).
Snapshot `~/bb2_cen/snap` from HEAD `f3ec41f3`, verified == oracle before measuring. Scripts:

## Method

1. **Static screen** for the two hazards measured on `text1a`: (a) a **≤8-byte extern declared
   as a scalar, living outside GPREL16 range of `$gp`, with its address taken** — at `-G8` cc1
   thinks it is 1-insn addressable and stops CSE-ing the base, but maspsx cannot rewrite it, so
   we pay a `lui` per use; (b) a **file-scope `__asm__` block**, which floats to the top of
   `.text` because `-G8` defers function bodies.
2. **Build pass** on candidates: `make GP_FILES=<stem> build/src/<stem>.o`, compared to the
   oracle object with the normalized method. Changed functions split into **regress** (carries
   no rules today, so it is byte-perfect from pure C and any change must be re-matched — what
   the two `text1a` siblings were) and **payoff?** (carries rules, so a change is a candidate
   improvement).
3. **Payoff verification**: honest pure-C distance measured with the engine sandbox at `-G0`
   and `-G8` for every payoff candidate. "Closer" is measured, never inferred.

**Screen calibration.** Post-adoption `text1a` screens at **1 offender, asm=N** (it needed 3
honest-type fixes + 1 extraction, all now done; the 1 residual is harmless — the file builds to
oracle). So **offender count is an upper bound on fix cost, not a hard block**: `BLOCKED` reads
as "needs N honest-type fixes first". 12 of 30 files screened PASS but all are trivial
(0–4 functions, ≤1 rule-carrying); the substantive files all carry offenders.

## `text1b` — the biggest prize, and it does not build

96 rule-carrying functions across 485 — by far the largest pool — but
`make GP_FILES=text1b` **fails to assemble**: `src/text1b.c:14: Warning: missing .end`, then
`used $at without ".set noat"`. That is hazard (b) biting hard: the file-scope `__asm__` block
floats out of position and desynchronises the `.set`/`.ent` state. It must be extracted to
`asm/funcs/` + a C stub + an `asmfix` `replace_with_asmfile` entry (the `save_vc_ctrl` recipe in
[[decBs0]]'s notes) before any payoff can even be measured. With 73 flagged externs it is also
the most expensive screen in the tree. **Highest ceiling, highest cost, currently unmeasured.**

## Standing caveats

- The screen is deliberately conservative (see calibration): it flags symbols whose address is
  taken anywhere in the file, not only those cc1 actually CSEs. Treat offender lists as a
  worklist to triage, not a count of required edits.
- Every adoption is a **per-file owner-approvable follow-up**, and each needs the full five-step
  recipe from [[decBs0]]'s notes — `MASPSX_FLAGS_GP` parity is already on main, so per file it
  is: `GP_FILES` entry → retype offenders → extract file-scope asm → re-match regressions →
  full-build SHA1.

## Adoption wave — 2026-08-05 (owner-approved follow-up to the census)

Snapshot `~/bb2_g8ad/snap` (from HEAD `3f937f2d`), verified == oracle before every
measurement. Scripts `tmp/csz/g8ad_*.{sh,py}`, `tmp/csz/t1b_*.{sh,py}`,

### Two screen defects found (they change how the table above should be read)

1. **The `asm=` column only detects `__asm__(`, not `asm(`.** `code6cac_c_mid`
   is reported `asm=-` but carries a file-scope `asm(".section .rodata / .space 4 /
   .previous")` at `src/code6cac_c_mid.c:894`, and that block is what breaks its
   jump-table layout at `-G8`. A tree-wide re-scan (`tmp/csz/g8ad_asmscan.py`)
   confirms `code6cac_c_mid` is the ONLY file affected by this spelling gap.
2. **The offender screen requires `&SYM`, so plain scalar accesses are invisible.**
   An out-of-GPREL16-range `≤8`-byte extern that is merely *read/written* (never
   address-taken) also degrades: at `-G0` cc1 CSEs its address into a register,
   at `-G8` it emits a 1-insn small-data reference that maspsx cannot rewrite and
   `as` expands per use. This is the mechanism behind BOTH the "regress" and the
   "farther" outcomes, and the screen does not flag it.
3. **Object-level comparison is blind to function reordering.** `tools/objdiff.py`
   normalizes relocs, so a function whose bytes are unchanged but whose *position*
   moved is scored "same". For files with file-scope asm the `changed` column
   therefore understates the damage badly — see `main` below.

### `text1b` — diagnosed, fixed, and NOT worth adopting

The build failure is **not** `.set`/`.ent` desynchronisation and **not** the 73
flagged externs. Root cause, proven:

- maspsx tracks `current_func` **only from `.ent`** (`tools/maspsx/maspsx/__init__.py:946`),
  and `_sdata_allowed_for_current_func` (line 452) refuses the `%gp_rel` rewrite when
  `current_func` is not in `sdata_funcs.txt`.
- `text1b` has **65 whole-body canonical-asm functions written as file-scope
  `__asm__` string blocks**. At `-G0` they sit after a preceding `.ent`, so the
  rewrite fires by adjacency. At `-G8` cc1 defers all function bodies: measured,
  every one of the 65 `glabel` blocks lands at cc1 lines 164–11400 while the first
  `.ent` is at line **11472** — so `current_func` is `None` for all of them.
- One block (`func_8006BD28`) contains bare small-data refs: **5 loads + 2 stores**.
  The 2 stores need `$at`, inside the block's own `.set noat` → the hard error
  (`{standard input}:12258: Error: macro used $at after ".set noat"`).

**Fix built and verified byte-neutral**: `tmp/csz/t1b_extract.py` extracts all 65
blocks to `asm/funcs/<f>.s` + C stubs + `asmfix.txt replace_with_asmfile` entries
(63 splat files already existed; 2 generated). One scripted run; **full build SHA1
== oracle at `-G0`**. Removes 9,623 lines of inline asm from `src/text1b.c`.
Artifacts: `tmp/csz/t1b_extract_out/`.

**With the fix, `text1b` builds at `-G8`** — and the prize evaporates:
`changed=41, regress=39, payoff?=2`, and both payoff candidates measure **same**
(`InitFadePanel` 3→3, `func_8004DDB4` 476→476). 39 re-matches for zero gain.
**Do not adopt.** The extraction itself is independently worth landing as a
representation cleanup.

### `code6cac_c_mid` — recipe COMPLETE, zero regressions

Two honest fixes collapse the blast radius from `changed=5 / regress=3` to
`changed=2 / regress=0` — i.e. only the two payoff functions move.

1. **`D_800F33D8` is a 0x200-byte buffer, not a `u8`.** Evidence: `func_80038148`
   zeroes 0x200 bytes from it via a walking `u8 *`; `func_80037C34(..., &X, 1,
   0x200, ...)` and `func_80037B90(..., &X, 0x200)` pass it with an explicit
   length; `camera_SetMatrix(&X + 0x100)` indexes its interior; `D_800A36EC =
   (u8 *)&X`. Fix: `extern u8 D_800F33D8[];`, 6 `&X` → `X`, and
   `return (s32 *)D_800F33D8;`. This alone removes `pad_FuncAnalog` from the
   regress list (it was paying a `lui`+`addiu` per use instead of one CSE'd base).
2. **Retire the `.space 4` rodata pad in favour of the natural `.align 3`.**
   Every jump table in the TU is already 8-byte aligned at its target offset
   (`.L156` 0xd8, `.L183` 0x108, `.L194` 0x138, `.L211` 0x168, `.L221` 0x198,
   `.L271` 0x1c8, `.L288` 0x210, `.L307` 0x240, `.L335` 0x270). cc1 emits
   `.align 3` before each; the `RODATA_ALIGN2_FILES` sed downgrades it to
   `.align 2`, which is a no-op for all of them EXCEPT `.L271` (0x1c4 → 0x1c8) —
   and that one gap is exactly what the hand-written pad filled. Fix: drop
   `code6cac_c_mid` from `RODATA_ALIGN2_FILES` and delete the `asm(...)` block.

Both fixes verified **byte-neutral at `-G0` (full build SHA1 == oracle)** and the
payoff reproduces: `func_80038170` 32 → **14**, `saSeInit_2` 58 → **56**.
Diffs banked at `tmp/csz/ccm_recipe/`.

**Remaining cost to land**: with `GP_FILES := text1a code6cac_c_mid` the full build
is **+8 bytes** — `func_80038170` and `saSeInit_2` are rule-carrying (INCOMPLETE)
and their regfix rules were tuned to the `-G0` emission, so they must be
re-matched. Inspection of `func_80038170` against target shows why the residual is
14 and not 0: target **mixes** the two base forms — `lui $at,%hi(D_8008F1A8) /
addu $at,$at,$a0 / lbu $v0,%lo(...)($at)` for one access, but a hoisted-and-reused
`lui $a1,%hi(D_8008F1C0)` for others. `-G0` gives all-CSE, `-G8` gives all-no-CSE;
neither is target, but `-G8` is 18 closer.

### `main` — STRUCTURAL BLOCKER, do not adopt as-is

`main.c` has 4 file-scope `__asm__` blocks (BIOS syscall trampolines at lines 1916,
2639, 3577, 3590). Measured on the cc1 stream: at `-G0` they sit at lines
5395–10123; at `-G8` they move to lines **359–558, ahead of the first `.ent` at
778**. `nm -n` on the objects confirms the consequence the object diff hides:

```
G0 first symbols: func_80083BE4 @0, D_800163D8 @0x18, ... g_data_start near the end
G8 first symbols: D_800163D8 @0, bios_DisableEvent @0, CheckFadeEnd @0x10,
                  bios_AddDevice_B @0x20, func_8008D060, g_data_start @0x30, ...
```

`g_data_start` — the `.text`/`.data` **boundary marker** — moves to offset 0x30.
The 4th block (line 3590) is not a plain trampoline: it also defines
`g_data_start`, `g_module_func_tbl` and `g_module_type_tbl`, i.e. the end-of-`.text`
table infrastructure. Extracting it needs care that the other three do not.

The 7 reported regressions split accordingly: `SetBloodSpot` and `func_8008AF9C`
are jump-table offset shifts (rodata reorder, hazard b), while `func_80085E4C`,
`func_80087CAC` and `func_8008BEA4` are lost-address-CSE (hazard a).
**Cost: 4 asm extractions incl. the boundary block + triage of 25 offenders +
re-match of 2 payoff functions, to buy −11 and −12.** Not recommended before
`code6cac_c_mid` lands.

### `code6cac_b` — the census's open question, answered

The 2 "farther" functions are **not** evidence of a mixed file or of a target that
prefers `-G0` semantics. Both degrade by the plain-access form of hazard (a) on
out-of-GPREL16-range scalars not in `sdata_syms.txt`:

- `func_80033DF4` — `D_80106A50` (gp+407940). `-G0`: `lui a0 / addiu a0,a0,0`
  once, reused for the load AND the store. `-G8`: a `lui` per access.
- `func_80034F88` — `D_80106A70` / `D_80106A73` (gp+407972).

`D_80106A50` is used as a struct base elsewhere in the same file
(`(struct HitRec *)&D_80106A50` at `code6cac_b.c:3664`, `a0 = &D_80106A50` at
3715/3733) with a flags word at offset 0 — so an honest struct declaration is
available and would very likely retire both regressions, exactly as the
`D_800F33D8` array fix retired `pad_FuncAnalog`.

**The 2 unmeasured payoff candidates are now measured** (they were
`payoff_names[:6]` truncation victims):

- `single_game_SetWazaData` 59 → **39** — a **−20**, the largest single win in the tree
- `func_8003504C` 30 → 31 (farther, marginal)

Revised `code6cac_b` picture: 8 candidates, **3 closer (−19, −20, −4 = −43 total)**,
2 same, 3 farther. That is the largest aggregate payoff of any file measured, and
the "farther" side looks fixable. `code6cac_b` should be re-ranked **above `main`**.
