## What the function actually is

A **bitstream reader** over a 3-word descriptor at `a0_param` — this is the VLC/bit-unpacker for the
`D_800A3D40` record table. Its only caller is `func_8003D7B4` (`src/code6cac_c2.c:1128-1150`), which
does `nbits = func_8003D888(base, 4); … val = (s16)func_8003D888(base, nbits);` in a 6-iteration
loop with sign extension — a textbook "read a 4-bit width, then read that many bits" decoder.

Descriptor layout, read straight off the target asm:

| offset | meaning |
|---|---|
| `+0x0` | `u32 *p` — pointer to the next word of the stream (`lw $a1,0($a2)`, `addiu $v0,$a1,4`, `sw $v0,0($a2)`) |
| `+0x4` | `u32 buf` — the current window word |
| `+0x8` | `s32 avail` — bits remaining in `buf` |

Semantics (both arms, transcribed from `asm/funcs/func_8003D888.s`):

```c
typedef struct { u32 *p; u32 buf; s32 avail; } BitStream;   /* declare it properly */

s32 getbits(BitStream *bs, s32 n) {
    s32 avail = bs->avail;
    if (avail < n) {                       /* slt $v0,$a1,$a3 ; beqz -> else arm */
        s32 rem   = n - avail;             /* subu $a3,$a3,$a1 */
        u32 lo    = bs->buf & ((1u << avail) - 1);   /* sllv/addiu -1 / and */
        u32 mask  = (1u << rem) - 1;                 /* sllv/addiu -1 */
        u32 *p    = bs->p;
        bs->p     = p + 1;                 /* addiu $v0,$a1,4 ; sw 0($a2) */
        bs->avail = 32 - rem;              /* addiu 0x20 ; subu ; sw 8($a2) */
        {   u32 next = *p;                 /* lw $a1,0($a1) */
            bs->buf = next;                /* sw $a1,4($a2)  <- in the j delay slot */
            return (lo << rem) | ((next >> (32 - rem)) & mask);
        }
    } else {
        bs->avail = avail - n;             /* subu $v0,$a1,$a3 ; sw 8($a2) */
        return (bs->buf >> bs->avail) & ((1u << n) - 1);
    }
}
```

Note the `1 << k` in **both** arms is materialised from the *same* `addiu $v0,$zero,1` in the taken
arm (`:7` sits in the `beqz` delay slot and is shared by both `sllv`s at `:9` and `:11`) but is
re-materialised separately in the else arm (`:36`) — so a single `s32 one = 1;` hoisted above the
`if` is *not* what target did; write `1u << k` naturally in each place and let cc1 hoist the taken
arm's pair itself.

## Static divergence hypothesis

With the current body: **everything**. The two injected `addu` blocks emit target's `:1`/`:2`
verbatim, so those 2 of 37 are "right" by construction; the remaining ~35 are whatever GCC does
with six pinned pseudos and a straight-line assignment soup — the pins fight the allocator
([[register-asm-pins]]) and the `__asm__` blocks act as scheduling fences, so neither the schedule
nor the allocation can land.

With an honest body, the residual should reduce to **one open question**: target's two leading
parameter copies

```
addu $a2, $a0, $zero
addu $a3, $a1, $zero
```

GCC 2.7.2 emits arg-hardreg → pseudo copies like this when the pseudos can't be coalesced with the
argument registers, which normally means the pseudo is live across something that conflicts. Both
copies survive here in a leaf with **no stack frame at all** (there is no `addiu $sp,$sp,-N` in the
prologue and no epilogue adjust — `:1` is already the first real instruction), so there is no spill
story. Most likely producer: the descriptor pointer and the count are held in locals whose live
ranges span the whole function including both arms of the `if`, while `$a0`/`$a1` get reused for the
window/word traffic inside the taken arm (target does exactly that — `$a0` becomes the mask at
`:11`, `$a1` becomes the loaded word at `:14`). So: **write `bs`/`n` as parameters used throughout,
and let the taken arm reuse fresh locals for the mask and the loaded word.** If the copies still
don't appear, that is the one thing to grind — slug `register-alloc-pure-c`, and
`param-reuse-base-copy-cse-canon` for the walker-style param reuse shape.

## SECOND LEVER

If the honest body lands close but keeps a handful of points, the likely candidates, in order:

1. **The two leading parameter copies** (above) — `register-alloc-pure-c`.
2. **`bs->buf = next;` placement.** Target puts `sw $a1, 0x4($a2)` in the `j .L8003D914` **delay
   slot** (`:26`), i.e. the store is scheduled after the `or`. Writing `bs->buf = next;` *before*
   the return expression is what lets cc1 sink it there; writing it after (or folding the return
   through a temp) will emit it early. Slug: `defer-store-past-later-compute-into-jal-delay` for the
   general shape, `store-before-jal` for the ordering recipe.
3. **`bs->avail = 32 - rem;` before the `lw $a1,0($a1)`.** Target interleaves
   `addiu $v0,$zero,0x20 / subu $v0,$v0,$a3 / lw $a1,0($a1) / sllv $v1,$v1,$a3 / sw $v0,8($a2)`
   (`:19-23`) — the `avail` store lands *after* the load and the shift. Statement order in the C is
   the lever; don't reach for a barrier.
4. **The `and` / `or` operand order** in `(lo << rem) | ((next >> shift) & mask)` — if a lone
   operand-order rename shows up, `compare-operand-order-register` is the family.
