**The rule cluster is not six unrelated findings — it is ONE divergence: a loop-invariant magic
constant that our build hoists out of the loop and target rematerialises inside it.**

`0x91A2B3C5` is the signed division magic for **÷1800**. Target materialises it **inside the loop
body, every iteration**, split across the load so the `ori` fills the `lw` load-delay slot

Our build hoists it to the preheader (hence `delete @13,@14` + re-`insert` at the loop top).

Contrast the other magic, `0x88888889` (**÷30**), which target **does** hoist
(`.s` `8003C740`/`8003C744`, `$a3`, then used by four `mult`s in the loop). So the target asymmetry is
**a four-use invariant hoisted, a one-use invariant not** — the classic loop.c `move_movables`
savings-vs-threshold split. Our build hoists both.

## Static divergence hypothesis

Shape comparison says the C is structurally right: 1 loop, 3 trip counts (`slti $v0,$t0,3` +
`bnez` at `.s` `8003C838`/`8003C83C`), 7 call sites (`func_80077D00`, `func_800372C0`,
`gpu_InitDisplay`, `func_80060758`, `func_8001CD68`, `disp_SetFramebufferMode`,
`gpu_DisableDisplay`) — all 7 present in the C in the same order. The three division chains match
the C exactly: `x/1800` (magic `0x91A2B3C5`, `sra 10`), `(x/30)%60` (`sra 4` then `sra 5` then
`×60` subtract), `((x%30)×100)/30` (`sra 4`, `×30` subtract, then `sll1+addu / sll3 + addu / sll2`
= ×100, then `sra 4`). Nothing is missing or stubbed.

So the **whole 33** should be attributable to the loop-invariant placement plus its knock-on
register rename. The rename range `@20-66` covers ~47 maspsx slots, which is why the distance is
large relative to a single-constant problem: one hoisting decision relabels every `mfhi` consumer
in the loop.

**Mechanism (needs one dump to confirm, do not guess further):** GCC 2.7.2 `loop.c move_movables`
scores each invariant by `m->savings` (number of in-loop references) against a `threshold` derived
from loop size / call presence. ÷30 has four references, ÷1800 has one. If our build hoists the
one-reference constant anyway, the cause is either (a) an inflated reference count for that pseudo
in our RTL, or (b) the hoist is happening in `cse.c`, not `loop.c`, in which case the recipe surface
is [[store-const-reload-cse]] / [[defeat-combine-symbol-fold]] rather than [[defeat-licm-hoist-var-reuse]].
The `-da` loop dump (or `BB2_ALLOC_DEBUG`-adjacent instrumentation — instrumented cc1 is
`tools/gcc-2.7.2/cc1`, **top-level, NOT `build/cc1`**, see [[instrumented-cc1-location]]) settles
(a) vs (b) in one run and is worth doing before any C edit beyond lever 1.

Slugs: [[defeat-licm-hoist-var-reuse]] (primary), [[store-const-reload-cse]] (alternate mechanism),
[[register-alloc-pure-c]] (the `$t1`/`$t2` residual, if it survives),

## FIRST LEVER

**Delete the three `register … asm()` pins (`:632-634`) and re-measure the honest floor
(`sandbox func_8003C714 --disable all`) before touching anything else.** They are uncommittable by
policy, they are the entire non-rule half of the cheat inventory, and the target's register choices
are exactly what unpinned locals should get anyway: `i`/`src`/`dst` are live only between the last
`jal` before the loop and the loop exit, they cross no call, and the natural caller-save picks in
`global.c find_reg` ascending order land on `$a1`/`$a2`/`$t0` — the target's registers. There is a
real chance the pins are *causing* part of the residual (a pinned `$t0` removes a hard reg from the
pool the `mfhi` destinations compete for, which is the `$t1` vs `$t2` question). Cheap, mandatory,
and diagnostic in one step. Capture the loop/`-da` dump in the same run.

## SECOND LEVER

**Stop the ÷1800 magic from being hoisted, without touching the ÷30 magic.** The honest C surface,
in order of preference:

1. **Reduce the ÷1800 chain's invariant footprint by re-reading the dividend where target re-reads
   it.** Target issues three separate `lw 0x4($a2)` (`.s` `8003C758`, `8003C77C`, `8003C7C8`) — the
   current C already does this (`:641`, `:642`, `:645`), so confirm the built RTL agrees rather than
   assuming it; if CSE has merged them into one pseudo, the merged value is what raises the
   invariant's reference count and [[split-read-defeats-hoist]] is the lever.
2. **[[defeat-licm-hoist-var-reuse]] proper** — reuse an existing scratch variable for the ÷1800
   dividend so loop.c cannot classify the constant's set as a clean movable.
3. **Loop-shape lever, last.** The already-adjudicated `CdControl` precedent
   (`docs/grind/decisions.md`, 2026-08-14 02:31) is the closest prior art in the tree: "the honest
   real-loop form measured WORSE ... because loop.c LICM hoists the invariant -1, and target
   materialises -1 in-loop ... so the original was not a loop.c-visible loop", and the accepted
   closing form used a single-level `do { … } while (0)` wrap. **That precedent does NOT transfer
   here as-is** — this function has a genuine 3-trip loop with a `bnez` back-edge, and its ÷30 magic
   *is* hoisted, which proves loop.c sees the loop. Read [[do-while-zero-exception]] before reaching
   for any wrapper, and only after 1 and 2 are measured.

Do **not** attempt to "move the cheat into C" by writing the `lui`/`ori` as an `__asm__` block —
