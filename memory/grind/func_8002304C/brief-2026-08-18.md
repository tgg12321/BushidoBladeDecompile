## Static divergence hypothesis (distance 29 of 216 insns)

29/216 ≈ 13% — the body is overwhelmingly right. The 29 decomposes as **A + B + C + D above, plus the
prologue schedule**, and the prologue is the largest single block:

Target prologue order (`8002304C`–`800230A8`) pairs each `sw $sN` with that register's **first
definition**, and the pairing order is:

```
s3=obj   s1=pos1   s2=pos2   fp=arg3      (params)
s0=0x1F8001B0   s5=0   s4=0x1F8001C0   s7=0x1F8002B8   s6=0x1F8001D0
```

The C declares them in a **different** order (`:2632-2635`): `scratch(0x1F8001B0)`,
`scratch_c(0x1F8001C0)`, `scratch_d(0x1F8001D0)`, `count`, and `0x1F8002B8` is not declared at all.
`.claude/rules/prologue-fix-redundant-reorder.md` states the mechanism outright: *"cc1's scheduler
pairs each callee-save's `sw $sN` immediately with that register's first definition, in the order
the defs appear in the C source."* So the current source order **cannot** produce the target
prologue — which is exactly why someone hard-coded the whole prologue into
`tools/prologue_config.json` and then pinned `s4`/`s5`/`s6` to compensate.

Note the untouched local `s32 *scratch` (`:2632`, no pin) *does* land in `$s0` at the right
prologue slot — proof that the named-local-pointer idiom works here and the pins are compensating
for ordering, not for an allocator wall.

## SECOND LEVER

**Family D — restore the `andi`.** Target reads `0x6A` once into `$a0` and derives a *masked* copy
`$v1` used only by the three equality tests, while the raw `$a0` feeds `mode - 0x17`. GCC 2.7.2
tracks narrowness **per register** (`redundant-byte-andi-satan0main`), so the mask survives only if
the tested pseudo is **not provably narrow**. The current C (`:2687-2689`) applies `& 0xFFFF` to an
already-`u16` local — a guaranteed no-op that GCC deletes. The lever is the *inverse* of the
saTan0Main fix: keep the raw read narrow (`u16 mode`) for the `-0x17` arm, and make the *tested*
value come from a full-range `s32` that GCC cannot narrow (e.g. a widening step through a value with
a non-`lhu` provenance), so the `andi` is real work. **Do NOT re-derive this from scratch** — read
`memory/reference/redundant-byte-andi-satan0main.md` first; it lists both the mechanism and the
levers that measurably failed.

Then, in order: family C via `store-before-jal` (hoist `s32 step;` out of the nested block at
`:2671-2682` to the top of the enclosing block so it is live at the join and its stack home is
emitted before the arg moves), and family B via `register-alloc-pure-c` Step-0 (`-da` greg dump) on
whatever `$t0`/`$v0` residue survives C.
