Read as a permutation: `{v1, a0, a1, a2} → {a2, v1, a0, a3}`. **This is not a rotation** — a
rotation would be the signature of one extra live value shifting everything by one. It is GCC
2.7.2 assigning these four quantities in a *different priority order*. Concretely: target allocates
the first-computed quantity (the table value / `abs_val`) LATE (`$a2`), while our build hands it
the first free caller-saved register (`$v1`); correspondingly target pushes every `mflo` result one
slot further out (`$a3` vs our `$a2`).

Confirm this against the asm directly — target `asm/funcs/func_80023648.s:44` `lh $a2, 0x0($v1)`
(the table value straight into `$a2`), `:118` `mflo $a3`, `:142`/`:151`/`:159` the other three
`mflo $a3`. Ours puts those in `$v1` and `$a2`.

## Static divergence hypothesis

Pure **register-allocation ordering**. Family: **`register-alloc-pure-c`** (global.c `find_reg`,
ascending order, priority ≈ `live_length × n_refs`). Because the instruction stream is already
byte-for-byte in the right order, **`tools/sched_solver` has nothing to do here** and
**`tools/ra_solver` is the near-ideal input** — validated model, single-mechanism residual, no
schedule noise to model around (`memory/project/ra-solver-campaign-2026-08-04.md`). The four
quantities are short-lived and block-local, so check `local_alloc.py` as well as the global path —
this is most likely a *local-alloc* ordering question (the same scope limit that stalled
`func_800858D0` before Phase 5 added local modelling).

Secondary slugs worth having in view but NOT currently divergent: `halfword-index-srl-sra` /
`strength-reduce-defeat` on `row = new_var + (a0 * 3)` (target `:36-42` `sll/addu/sll/addu/sll/addu`

## FIRST LEVER

**Split the overloaded `abs_val` slot.** `src/code6cac.c:2848` declares `s32 abs_val`, uses it for
the `0x400` clamp, and then line 2874 reuses the *separate* `sub_result` local for a second,
unrelated value (`sub_result = *(s16 *)(arg0 + 0x1A);` after it already held `0x14E - abs_val`).
Two named locals are each carrying two logically distinct values across the block, which is exactly
what inflates `live_length` and drives them to the front of the priority order. Give each value its
own once-written local (`abs_val` clamp result / `sub_result` subtraction / a fresh `raw_1a` for the
reload). This is free — no new construct, no FAKE annotation, shorter live ranges, and it directly
attacks the `$v1→$a2` group (11 of the 30 rules) and the `$a1→$a0` group (5 more).

## SECOND LEVER

**Give each `mflo` product its own short-lived local.** All four multiplies currently funnel through
the shared `mult_res` (2872) / `speed_prod` (2883) pattern and feed straight into a shift. Target
keeps every one of them in `$a3` — the *last* caller-saved register, i.e. allocated last. Naming
each product into its own local is the standard way to push a quantity later in the allocation
order, and it targets the 7-rule group 4 plus the 3-rule group 5 (10 of 30).
